CI/CD · Que lo publique GitHub

Antes de empezar

Usa Catálogos para todo el CFP: el programa que arma los catálogos. Y lo que viste de tests en Testing I.

El problema

Sección titulada «El problema»

Es la Expo, son las seis de la tarde, y alguien de Pastelería completa el formulario desde el celular. Una preceptora lo revisa y tilda Aprobado. ¿Y ahora?

Hasta acá, el catálogo aparece cuando alguien baja la planilla, corre generar.py en su compu y sube el resultado. Si nadie lo hace, no aparece. Y si lo hace con un error en el programa, se publica roto.

Lo que queremos: que cada hora, sin que nadie apriete nada, una computadora pruebe el programa, lo corra y publique el resultado. Y que si algo anda mal, no publique nada.

CI y CD

Sección titulada «CI y CD»

Son dos ideas, y casi siempre van juntas:

  • CI, integración continua (continuous integration): cada vez que cambia el código, una computadora corre los tests sola. Si alguno falla, avisa enseguida: el error aparece cuando se cometió, y no tres semanas después.
  • CD, entrega continua (continuous delivery/deployment): si los tests pasan, esa misma computadora publica el resultado. Sin pasos a mano, que es donde se cuelan los errores (subir la carpeta equivocada, olvidarse un archivo).

Juntas forman una cañería (pipeline): bajar el código → instalar lo que hace falta → los tests → generar → publicar. Cada paso se hace solo si el anterior salió bien.

GitHub Actions

Sección titulada «GitHub Actions»

GitHub tiene computadoras que presta gratis para esto. Se les dice qué hacer con un archivo en el repo, en .github/workflows/, escrito en YAML: un formato para escribir datos con sangría, como un diccionario de Python sin llaves.

Este es el de los catálogos, por partes.

Cuándo corre: on

Sección titulada «Cuándo corre: on»

Son los disparadores. Tres cosas lo hacen correr: el reloj, un botón, y un cambio en el código.

El cron es una forma muy vieja (de los años 70) de decir “cada cuánto”. Son cinco campos: minuto, hora, día, mes y día de la semana, y * quiere decir “cualquiera”:

cronCuándo
17 * * * *En el minuto 17 de cada hora
0 9 * * *Todos los días a las 9:00 (hora UTC: 6:00 en Argentina)
0 9 * * 1Los lunes a las 9:00 UTC

Dónde y qué: jobs y steps

Sección titulada «Dónde y qué: jobs y steps»

Cada paso (step) es una de dos cosas:

  • run: un comando, el mismo que escribirías en la terminal.
  • uses: una acción que ya hizo alguien (bajar el código, instalar Python, publicar en GitHub Pages). Es como un import: usás algo hecho en vez de escribirlo.

La compu que presta GitHub se llama runner. Arranca vacía, hace los pasos en orden, y al terminar se borra. Por eso el primer paso es bajar el código: no tiene nada.

Los tests que cuidan la publicación
Sección titulada «Los tests que cuidan la publicación»


En la cañería, los tests son la red de seguridad: lo único que está entre un error y un catálogo
roto en internet. Y un test que no prueba los casos difíciles es una red con agujeros.


precio() convierte lo que escribió la persona en el formulario en lo que se muestra: "4500" →
"$4.500", y si lo dejó vacío, "Consultar". Parece fácil, pero la gente escribe cualquier cosa.


 
 🌳 
La red de seguridad del precio
 ⭐ Fundamental ✓ Resuelto 
 
 
Escribí los assert que pasen con la versión correcta y atrapen las cuatro versiones rotas.
Cada versión rota es un error que podría llegar a internet si nadie lo prueba.
 
 
 👀 Ver la función que vas a probar 
import re

def precio(valor):
  entero = str(valor).split(",")[0]
  digitos = re.sub(r"\D", "", entero)
  if not digitos or int(digitos) == 0:
      return "Consultar"
  return "$" + f"{int(digitos):,}".replace(",", ".")
 

Esta función no se toca. Vos escribís los assert que la ponen a prueba.

    Para llevar
    Sección titulada «Para llevar»
    

      

    • CI: una computadora corre los tests cada vez que cambia el código. CD: si pasan, publica.
Juntas, una cañería que se corta en el primer paso que falla.
      • 

    • En GitHub, la cañería es un workflow en .github/workflows/, en YAML: cuándo corre (on:
el reloj con cron, un botón, un cambio) y qué hace (steps, con run o uses).
      • 

    • Los tests van antes de publicar: si uno falla, en internet queda lo de antes.
      • 

    • Las llaves y contraseñas van en secretos, nunca en el código. Si una se publica, se anula.
      • 

    • Antes de publicar se revisa el programa (los tests) y también los datos: lo roto se saltea, y
queda dicho por qué.
