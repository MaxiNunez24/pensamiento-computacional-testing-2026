Cómo encarar estos tres

Sección titulada «Cómo encarar estos tres»

Los de acá son más difíciles que los de la clase anterior, y con todos te va a pasar lo mismo: la primera solución te va a salir en cinco minutos y va a andar. La segunda te va a llevar más, y es la que importa.

El orden de trabajo es siempre el mismo:

🧩

Los pasos para optimizar

✓ Resuelto

Ordená los pasos del método. Uno de ellos va al final por un motivo muy concreto: las soluciones rápidas se rompen más que las lentas.

  1. Encontrar QUÉ es lo que se está repitiendo de más
  2. Hacer que ande, como salga
  3. Reescribir con la idea nueva, y volver a medir
  4. Medir y mirar la forma: ¿el trabajo crece igual que los datos, o mucho más rápido?
  5. Comprobar que los tests siguen pasando
  6. Preguntarse si esa información se puede saber sin volver a recorrer

💡 Pistas
  1. Optimizar algo que todavía no anda es optimizar cualquier cosa: no sabés si el camino que estás haciendo más rápido es el correcto.
  2. El último paso no es opcional. Es facilísimo hacer una versión veloz que dejó de dar el resultado bien.
🌳

¿Es primo?

✓ Resuelto

Escribí es_primo(n): True si n es primo, False si no.

Hacelo andar primero de la forma obvia. Después mirá la medición del segundo escenario y buscá la idea que lo cambia todo — es de matemática de la secundaria, no de programación.

 💡 Pistas para pensar el costo 
     
  1. Lo directo es probar todos los divisores del 2 al n - 1. Con n de un millón, eso es un millón de vueltas para responder una pregunta de sí o no.
  2. Agarrá el 36 y escribí todas sus parejas de divisores: 2×18, 3×12, 4×9, 6×6, 9×4, 12×3, 18×2. ¿Notás que a partir del 6 se empiezan a repetir dadas vuelta?
  3. Ese 6 es la raíz cuadrada de 36. Si un número tiene un divisor más grande que su raíz, entonces también tiene uno más chico — y a ese ya lo ibas a encontrar antes. ¿Hasta dónde te alcanza con probar?
  4. Para no importar nada: en vez de i <= raiz(n) podés preguntar i * i <= n. Es la misma condición.

Probar todos los divisores
 
if n < 2:
    return False
for i in range(2, n):
    if n % i == 0:
        return False
return True
 
⏱️ más de 300.000 pasos con n = 999.983 (lo cortamos: eran unos 2.000.000)
 
Correcto y carísimo. Para un número primo hace todas las divisiones, porque nunca encuentra una que corte.
 
 
Hasta la raíz cuadrada
 
if n < 2:
    return False
i = 2
while i * i <= n:
    if n % i == 0:
        return False
    i += 1
return True
 
⏱️ unos 3.000 pasos con n = 999.983
 
El número creció 100 veces y el trabajo solo 10. Esa es la forma más linda que vas a ver en el curso: cuanto más grande el problema, proporcionalmente menos trabajás.
 
 
Y encima, saltear los pares
 
if n < 2:
    return False
if n == 2:
    return True
if n % 2 == 0:
    return False
i = 3
while i * i <= n:
    if n % i == 0:
        return False
    i += 2
return True
 
⏱️ unos 1.500 pasos
 
Si no es divisible por 2, tampoco lo va a ser por 4, 6, 8… Probar solo los impares parte el trabajo al medio. Es una mejora real, pero de otro tipo: no cambia la forma de la curva, solo la baja. La de la raíz cuadrada sí cambia la forma.

Contar cada letra
 ✓ Resuelto   
 
 
Escribí contar_letras(texto), que devuelve un diccionario con cuántas veces aparece cada letra.
Con "aba" tiene que devolver {"a": 2, "b": 1}.
Y una advertencia honesta sobre este en particular: acá la insignia te puede mentir. Si tu
solución llama a texto.count(...) adentro del for, el medidor te va a poner un ⚡ y en realidad
va a ser la peor de todas. Cuando termines, leé el último de los “otros caminos” — es el más
importante de toda la clase.
 
 
 📶 La primera vez se descarga Python (unos 10 MB). Si estás con datos del celular, mejor esperá a tener WiFi. Después queda guardado y ya no se baja más.

  • contar_letras("abcdefghij" * 300) — texto de 3.000 letras

 💡 Pistas para pensar el costo 
     
  1. Con una sola pasada alcanza: por cada letra, o la agregás al diccionario con un 1, o le sumás uno a lo que ya tenía.
  2. Si tu solución recorre el texto una vez por cada letra distinta, estás recorriendo el mismo texto muchas veces. ¿Hace falta?
  3. Los diccionarios tienen .get(clave, valor_por_defecto): devuelve lo que haya, y si no hay nada devuelve el valor que le pases. Con eso el if desaparece.
    4.  
 
 
 🔬 Otros caminos, y lo que cuesta cada uno 

Todos estos funcionan. La diferencia está en lo que le hacen hacer a la
        máquina.

 
 
Una pasada, armando el diccionario
 
cuentas = {}
for letra in texto:
    if letra in cuentas:
        cuentas[letra] += 1
    else:
        cuentas[letra] = 1
return cuentas
 
⏱️ unos 9.000 pasos con 3.000 letras
 
Tres líneas por letra, una sola vuelta. Es la solución que hay que saber escribir.
 
 
Lo mismo pero más corto
 
cuentas = {}
for letra in texto:
    cuentas[letra] = cuentas.get(letra, 0) + 1
return cuentas
 
⏱️ unos 6.000 pasos
 
Misma idea, una línea menos por vuelta. No cambia la forma de la curva, pero se lee mejor.
 
 
La que ya viene hecha
 
from collections import Counter

def contar_letras(texto):
    return dict(Counter(texto))
 
⏱️ 1 paso tuyo
 
Counter es parte de la librería estándar de Python: hace exactamente esto y está escrito en C. Antes de programar algo, siempre vale la pena preguntarse si no está hecho.
 
 
⚠️ El camino donde el medidor te miente
 
cuentas = {}
for letra in texto:
    cuentas[letra] = texto.count(letra)
return cuentas
 
⏱️ unos 6.000 pasos según el medidor… y es la PEOR de todas
 
Cada texto.count(letra) recorre el texto entero, pero como count está escrito en C el contador lo ve como un solo paso. En realidad esto recorre 3.000 letras, 3.000 veces: nueve millones de comparaciones. Moraleja: el medidor cuenta tus líneas, no el trabajo escondido adentro de las funciones. Cuando llames a algo que recorre, pensá vos cuántas veces lo estás llamando.

Sacar repetidos sin perder el orden
 ✓ Resuelto   
 
 
Escribí sin_repetidos(items), que devuelve la misma lista pero sin elementos repetidos,
respetando el orden en que aparecieron.
Con [1, 2, 1, 3, 2] tiene que devolver [1, 2, 3].
 
 
 📶 La primera vez se descarga Python (unos 10 MB). Si estás con datos del celular, mejor esperá a tener WiFi. Después queda guardado y ya no se baja más.  
   
 ⏱️ Lo vamos a medir con: 
     
  • sin_repetidos([i % 40 for i in range(80)]) — 80 items (40 distintos)
  • sin_repetidos([i % 200 for i in range(400)]) — 400 items (200 distintos)

 💡 Pistas para pensar el costo 
     
  1. Un set(items) saca los repetidos de una… pero se lleva puesto el orden. Acá el orden importa, así que el set no puede ser el resultado: tiene que ser tu anotador.
  2. Recorré la lista una vez y llevá dos cosas al mismo tiempo: la lista que vas armando (donde importa el orden) y un conjunto de los que ya viste (para preguntar rápido).
  3. ¿Por qué no preguntarle directamente a la lista que vas armando, con if x not in resultado? Anda, pero not in sobre una lista la recorre entera cada vez. El medidor no te lo va a marcar; la máquina sí lo paga.
    4.  
 
 
 🔬 Otros caminos, y lo que cuesta cada uno 

Todos estos funcionan. La diferencia está en lo que le hacen hacer a la
        máquina.

 
 
Buscar a mano entre los que ya guardé
 
resultado = []
for x in items:
    ya_esta = False
    for y in resultado:
        if x == y:
            ya_esta = True
    if not ya_esta:
        resultado.append(x)
return resultado
 
⏱️ más de 100.000 pasos con 400 items
 
La grilla otra vez: por cada item, recorrés todo lo que llevás guardado. Y encima no corta cuando lo encuentra.
 
 
Lista para el orden, set para preguntar
 
resultado = []
vistos = set()
for x in items:
    if x not in vistos:
        resultado.append(x)
        vistos.add(x)
return resultado
 
⏱️ unos 1.200 pasos con 400 items
 
Cada estructura hace lo que sabe hacer: la lista guarda el orden, el set responde "¿ya lo vi?" al instante. Esta combinación aparece por todos lados una vez que la conocés.
 
 
El truco de los diccionarios
 
return list(dict.fromkeys(items))
 
⏱️ 1 paso tuyo
 
Desde Python 3.7 los diccionarios recuerdan el orden en que se agregaron las claves, y las claves no se repiten. Así que un diccionario armado con los items ya es, exactamente, la lista sin repetidos y en orden.
 
 
  
 



Lo que te llevás
Sección titulada «Lo que te llevás»


    

  1. Primero que ande. Después se mejora. Nunca al revés.
    2. 

  2. Un bucle adentro de otro que recorre lo mismo es la señal de alarma número uno.
    3. 

  3. La solución barata casi nunca es la misma solución más prolija: es otra idea. Suele aparecer
cuando te preguntás “¿puedo saber esto sin volver a mirar todo?”.
    4. 

  4. Usá lo que ya está hecho. set, dict, max(…, key=…), Counter: están escritos en C y
pensados por gente que le dedicó mucho tiempo.
    5. 

  5. Contá las llamadas, no solo las líneas. Si adentro de un for llamás a algo que recorre
(.count(), in sobre una lista, sorted()), el costo está ahí aunque no lo veas.
    6.
