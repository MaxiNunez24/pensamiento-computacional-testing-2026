Testing I — probar en serio

Todos ustedes ya probaron sus programas. Los corrieron, escribieron algo, miraron la pantalla y dijeron “anda”. Eso es probar. Lo que cambia acá es quién lo hace: en vez de vos cada vez, lo hace el programa, siempre igual y sin cansarse.

¿Por qué esto tiene una clase entera?

Porque el curso se llama Pensamiento Computacional y Testing de Aplicaciones. Y porque el día que el sistema de asistencias tenga 40 pantallas, probarlo a mano después de cada cambio va a ser imposible.

Lo que ya venís haciendo sin saberlo

Sección titulada «Lo que ya venís haciendo sin saberlo»

Cada vez que tocás Verificar en un ejercicio, se corre un test. El botón no mira si tu código “está lindo”: corre tu función con valores concretos y compara el resultado con el esperado. Eso es todo lo que es un test.

assert significa “afirmo que esto es verdad”. Si lo es, no pasa nada. Si no lo es, el programa se detiene y avisa. Un test es una afirmación sobre tu código.

Tres alturas para mirar lo mismo
Sección titulada «Tres alturas para mirar lo mismo»


Un programa se puede probar de a pedacitos o entero, y las dos cosas sirven para distinto.


 
 🟡 
¿Unitaria, de integración o de punta a punta?
 ✓ Resuelto 
 
 
Arrastrá cada caso a la altura que le corresponde.
 
 

Tocá una tarjeta y después la caja donde va. Con mouse también podés arrastrarla. 
 
  
 
 
 
 🔩 Prueba unitaria una pieza sola, aislada 
 
 
 
 🔗 Prueba de integración dos o más piezas trabajando juntas 
 
 
 
 🚦 Punta a punta (E2E) el sistema entero, como lo usa una persona 
 
 
 
 
   
 
 💡 Pista 
  • Preguntate cuántas piezas tuyas participan: una sola, varias, o el sistema completo.
  • Si para probarlo hace falta abrir el navegador, casi seguro es de punta a punta.
 
 
 
     
     

    La regla práctica
    Muchas unitarias (son baratas y rápidas), algunas de integración, pocas de punta a punta:
son las más lentas y las que más se rompen por cualquier cosa.
    

    Ahora escribís vos
    Sección titulada «Ahora escribís vos»
    

    Acá está la parte que importa. Un test no se juzga por lo que dice, sino por lo que
detecta: tiene que pasar con el código que anda y fallar con el código roto. Si no
distingue uno del otro, no sirve, por más lindo que se vea.
    

     
     🟠 
    El test que atrapa el bug
     ✓ Resuelto 
     
     
    Escribí los assert necesarios para que pasen con la versión correcta y fallen con
las tres versiones rotas. Abajo vas a ver cuáles atrapaste y cuál se te escapó.
     
     
     👀 Ver la función que vas a probar 
    def promedio(notas):
  if not notas:
      return 0
  return sum(notas) / len(notas)
     
    
Esta función no se toca. Vos escribís los assert que la ponen a prueba.

     
     
     
        
     
     💡 Pista 
    • Con un solo caso no alcanza: promedio([10, 10]) da 10 tanto en la versión buena como en la que suma sin dividir… ¿o no? Probalo.
    • Pensá en los bordes: ¿qué pasa con la lista vacía? ¿Y con un solo elemento?
    • Un promedio no siempre da un número redondo. Probá con [7, 8].
     
     
     
       
       
       

      Lo que acabás de descubrir
      Un test que pasa no significa que el código esté bien: significa que ese caso anda.
Por eso los bugs se escapan — no porque nadie pruebe, sino porque nadie probó ese caso.
