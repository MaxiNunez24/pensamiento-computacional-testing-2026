## El programa se cae

Esto ya te pasó muchas veces:

```python
edad = int("doce")
```

```text
Traceback (most recent call last):
  File "main.py", line 1, in <module>
ValueError: invalid literal for int() with base 10: 'doce'
```

El programa se frena ahí, en esa línea, y no sigue. Lo que Python está diciendo es: **"me pediste
algo que no puedo hacer"**. Eso se llama una **excepción**.

Hasta ahora, cuando aparecía una, la solución era arreglar el código. Pero en el sistema del CFP
los datos **no los escribimos nosotros**: los escriben treinta personas en un formulario, y alguna
va a poner *"doce"* donde iba un número. El programa no puede caerse cada vez que pasa eso.

## Las que ya conocés

Cada excepción tiene **un nombre**, y el nombre ya te dice qué pasó:

| Excepción | Cuándo aparece | Ejemplo |
|---|---|---|
| `ValueError` | El tipo está bien, pero **el valor no sirve** | `int("doce")` |
| `TypeError` | Mezclaste **tipos** que no van juntos | `"Tenés " + 3` |
| `KeyError` | Esa **clave** no está en el diccionario | `alumno["apelido"]` |
| `IndexError` | Esa **posición** no existe en la lista | `[1, 2, 3][10]` |
| `ZeroDivisionError` | Dividiste por **cero** | `presentes / 0` |

## Atajarla: try y except

`try` quiere decir *"intentá"*. Se pone alrededor de lo que puede salir mal, y abajo, en `except`,
lo que hay que hacer **si sale mal**:

```python
texto = "doce"
try:
    edad = int(texto)
    print("Tiene", edad, "años")
except ValueError:
    print("Eso no es un número")
```

Si `int()` puede, se sigue normal y el `except` no se ejecuta. Si no puede, **Python salta directo
al `except`** —lo que quedaba del `try` no se ejecuta— y el programa **sigue vivo**.

## Nunca un except solo

Se puede escribir `except:` sin nombre, y ataja **cualquier** excepción. Parece más cómodo. No lo es:

```python
def a_numero(texto):
    try:
        return int(textto)      # ← un error de tipeo: "textto"
    except:
        return None
```

Esa función **siempre** devuelve `None`, para cualquier texto. El error de tipeo tira un `NameError`,
el `except:` lo ataja callado, y nadie se entera de que el programa está roto.

## Levantar las tuyas: raise

Hasta acá **atajaste** excepciones. Ahora al revés: las vas a **levantar** vos.

En la clase del bot, el `Alumno` decía si estaba listo con `problemas()`. Pero hay datos que están
tan rotos que el alumno **no debería ni existir**: un DNI con letras no es un alumno a medio cargar,
es un error. Para eso está `raise`:

```python
class Alumno:
    def __init__(self, dni, apellido, nombre):
        if not dni.isdigit():
            raise ValueError("el DNI tiene que ser solo números")
        self.dni = dni
```

`raise` **corta el `__init__` ahí mismo**. El objeto no llega a crearse, y quien lo quiso crear
recibe un `ValueError` con tu mensaje. Es la misma excepción que tira `int("doce")`, porque es el
mismo problema: el valor no sirve.

## Atajar, anotar y seguir

Con el `Alumno` que ya no acepta cualquier cosa, falta lo último: que **un alumno roto no frene a
los demás**. Es lo que hace el bot: los que están bien se cargan, y los rotos quedan anotados con su
motivo para que los mire una persona.

El truco es `except ... as e`: además de atajar la excepción, **te la guarda** en `e`, con su
mensaje adentro.

```python
try:
    alumno = Alumno("40.000.010", "Sosa", "Camila")
except ValueError as e:
    print("No se pudo:", e)     # No se pudo: el DNI tiene que ser solo números
```

## Para llevar

- Una **excepción** es Python diciendo *"no puedo hacer esto"*. Su **nombre** dice qué pasó.
- **`try`** alrededor de lo que puede fallar; **`except NombreDelError:`** con lo que hay que hacer si
  falla. El programa sigue vivo.
- **Nunca `except:` solo**: se come tus propios errores y los esconde.
- **`raise ValueError("...")`** frena todo cuando un dato no sirve. Un `Alumno` con el DNI roto no
  llega a existir.
- **`except ... as e`** te guarda la excepción: con eso anotás el motivo y seguís con el siguiente.
