## El problema: código repetido

`Perro` y `Gato` comparten nombre, edad y `comer()`, y solo cambian el sonido. Escribir todo dos
veces es un desperdicio. La **herencia** te deja escribir lo común **una sola vez**.

## Herencia: heredar para no repetir

```python
class Animal:                  # clase MADRE (lo común)
    def __init__(self, nombre):
        self.nombre = nombre
    def comer(self):
        return f"{self.nombre} está comiendo"

class Perro(Animal):           # Perro HEREDA de Animal
    def hacer_sonido(self):
        return f"{self.nombre} dice: ¡Guau!"
```

`class Perro(Animal)` se lee *"Perro **es un** Animal"*. Perro no escribió `__init__` ni `comer()`,
pero los **tiene** (los heredó). Si la hija define un método que ya existía, el suyo **gana**: eso es
**sobrescribir** (override). Y con **`super().__init__(...)`** reusás el constructor de la madre
cuando la hija necesita un atributo más.

## Polimorfismo: misma orden, distinta respuesta

Objetos distintos que responden a la **misma orden**, cada uno a su manera. Como comparten la
interfaz, podés tratarlos a todos por igual:

```python
for animal in [Perro("Fido"), Gato("Michi")]:
    print(animal.hacer_sonido())   # no preguntamos de qué tipo es: cada uno sabe
```

Vamos a verlo **entre archivos**: definís las figuras en `formas.py` y en otro recuadro las importás
y sumás sus áreas con un solo `for`.

## Para llevar

- `class Hija(Madre):` hereda todo; sobrescribís lo que cambia; `super().__init__(...)` reusa el
  constructor de la madre.
- **Polimorfismo**: misma interfaz, distinta respuesta → un `for` sirve para objetos de tipos
  distintos.
- En UML, la herencia es la flecha `▷` ("es un").
