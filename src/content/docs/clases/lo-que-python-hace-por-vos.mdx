Cuando empecemos con el sistema van a aparecer cosas raras: un `@` colgado arriba de una función,
un `with`, un `try`. No son magia y **no son obligatorias**: son atajos para escribir menos.

Esta clase muestra cada atajo **al lado de cómo sería sin él**. Esa es toda la idea:

:::tip[La regla para no asustarse nunca más]
Si podés escribir la versión larga, entendiste el atajo. Y si algún día el atajo falla, sabés
exactamente qué estaba haciendo por vos.
:::

## 1. El `@` — decoradores

Es lo que más impresiona y lo más simple de los cinco.

```python
@app.route("/lista")
def lista():
    return "hola"
```

### Sin el atajo

Esas dos líneas son **exactamente** esto:

```python
def lista():
    return "hola"

lista = app.route("/lista")(lista)
```

Se define la función normal, y después se la **manda a otra función** que hace algo con ella. El
`@` es solo una forma más corta de escribir esa última línea.

### Por qué existe

Porque `lista = app.route("/lista")(lista)` es feo, es fácil de olvidar, y queda **abajo** de la
función — o sea, lejos de donde uno la lee. El `@` lo pone arriba, donde se ve.

### Hacete uno

Un decorador es **una función que recibe una función y devuelve otra**. Nada más.

## 2. El `with` — abrir y cerrar sin olvidarse

Lo vas a ver en cuanto trabajemos con archivos.

```python
with open("datos.txt") as f:
    contenido = f.read()
```

### Sin el atajo

```python
f = open("datos.txt")
try:
    contenido = f.read()
finally:
    f.close()          # esto SIEMPRE tiene que pasar
```

### Por qué existe

Porque **todo el mundo se olvida de cerrar el archivo**. Y si el programa falla en el medio, el
`close()` nunca se ejecuta: el archivo queda abierto, y en Windows eso significa que después no lo
podés ni borrar ni abrir con otro programa.

El `with` garantiza el cierre **aunque explote todo lo de adentro**. Por eso es la forma
recomendada, no una preferencia de estilo.

:::note[Dónde lo vas a usar]
En el sistema, cada vez que guardemos o leamos los datos. Va a estar en todos lados.
:::

## 3. `try` / `except` — cuando algo puede salir mal

```python
try:
    edad = int(input("Tu edad: "))
except ValueError:
    print("Eso no era un número")
```

### Sin el atajo

No hay versión larga: **sin `try`, el programa se corta**. Lo único que podés hacer es revisar
antes:

```python
texto = input("Tu edad: ")
if texto.isdigit():
    edad = int(texto)
else:
    print("Eso no era un número")
```

### Cuándo cada uno

| | Cuándo conviene |
|---|---|
| **`if` antes** | Cuando podés preguntar barato: ¿la lista está vacía? ¿es un número? |
| **`try`** | Cuando no podés saberlo sin intentar: abrir un archivo, hablar con internet, convertir algo raro |

> Nadie puede saber si un archivo se va a poder abrir sin intentar abrirlo. Entre que preguntás
> "¿existe?" y lo abrís, alguien lo pudo haber borrado. Por eso ahí va `try`.

## 4. `__init__` y `self` — el molde de los objetos

Esto llega con POO, y es lo que más ruido hace.

```python
class Alumno:
    def __init__(self, dni, apellido):
        self.dni = dni
        self.apellido = apellido

a = Alumno("***REMOVED***", "***REMOVED***")
print(a.apellido)
```

### Sin el atajo

Lo mismo, con un diccionario:

```python
def crear_alumno(dni, apellido):
    return {"dni": dni, "apellido": apellido}

a = crear_alumno("***REMOVED***", "***REMOVED***")
print(a["apellido"])
```

**Funciona igual.** Y hasta que el sistema crece, es más simple.

### Por qué existe entonces

Por dos cosas que el diccionario no te da:

1. **Los datos y lo que se puede hacer con ellos viajan juntos.** `a.nombre_completo()` está al
   lado de `a.apellido`. Con diccionarios, la función anda suelta por ahí.
2. **El molde obliga.** Si `__init__` pide `dni` y `apellido`, no podés crear un alumno sin
   apellido. Con un diccionario sí, y te enterás tres pantallas después.

### Y `self`, ¿qué es?

**Es el objeto mismo.** Cuando escribís `a.nombre_completo()`, Python por detrás hace:

```python
Alumno.nombre_completo(a)      # ← 'a' entra como self
```

Por eso `self` es el primer parámetro de todos los métodos: **es el objeto sobre el que estás
trabajando**. No es una palabra reservada, es un parámetro común — podrías llamarlo distinto, pero
todo el mundo lo llama `self` y conviene no innovar ahí.

## 5. Comprensiones de lista

```python
pares = [n for n in numeros if n % 2 == 0]
```

### Sin el atajo

```python
pares = []
for n in numeros:
    if n % 2 == 0:
        pares.append(n)
```

### Por qué existe

Porque el patrón "recorrer, filtrar, guardar en una lista nueva" aparece **todo el tiempo**, y en
una línea se lee de un vistazo.

:::caution[La trampa]
Es tentador meter todo adentro. Si tu comprensión necesita dos `if` y un `for` anidado, **escribí
el `for` largo**: el atajo dejó de ahorrar y empezó a esconder.
:::

## 6. Los atajos chicos que te van a ahorrar mucho

### `.get()` en diccionarios

```python
estado = asistencia.get(dni, "")      # si no está, devuelve ""
```

Sin él:

```python
if dni in asistencia:
    estado = asistencia[dni]
else:
    estado = ""
```

**Por qué importa en el sistema:** cuando preguntás por un alumno que todavía no fue marcado,
`asistencia[dni]` **explota**. Con `.get()` devuelve vacío y seguís.

### `enumerate` — el número de orden

```python
for numero, alumno in enumerate(alumnos, start=1):
    print(numero, alumno)
```

Sin él:

```python
numero = 1
for alumno in alumnos:
    print(numero, alumno)
    numero += 1
```

**En el sistema:** la columna N° de la planilla sale de acá.

### `zip` — dos listas a la vez

```python
for nombre, nota in zip(nombres, notas):
    print(nombre, nota)
```

Sin él:

```python
for i in range(len(nombres)):
    print(nombres[i], notas[i])
```

### `any` y `all` — ¿alguno? ¿todos?

```python
tiene_mayuscula = any(c.isupper() for c in password)
cumple_todo     = all([largo_ok, tiene_mayus, tiene_num, sin_espacios])
```

Sin ellos:

```python
tiene_mayuscula = False
for c in password:
    if c.isupper():
        tiene_mayuscula = True

cumple_todo = largo_ok and tiene_mayus and tiene_num and sin_espacios
```

**En el sistema:** *"¿algún día del mes quedó sin cargar?"* es un `any`. *"¿todos los alumnos
tienen DNI?"* es un `all`.

:::caution[Con la lista vacía contestan al revés de lo que uno espera]
`any([])` da **False** y `all([])` da **True**. Suena raro, pero es lo único coherente: si no hay
ninguno, no hay ninguno que cumpla (`any` → False) y no hay ninguno que falle (`all` → True).

Es el mismo caso borde de siempre: **el curso sin alumnos, el mes sin cargar, la lista vacía.**
:::

## 7. `if __name__ == "__main__":`

```python
if __name__ == "__main__":
    app.run()
```

Significa: **"esto corre solo si ejecutás ESTE archivo directamente"**, y no si otro archivo lo
importa.

### Por qué lo vas a necesitar

Cuando escribamos los tests, el archivo de tests va a hacer `import app`. Sin esa línea, importarlo
**arrancaría un servidor web** en medio de los tests y todo se colgaría.

Es la diferencia entre *"corré este programa"* y *"prestame tus funciones"*.

## Para llevarse

:::tip[Lo único que hay que recordar]
Ninguno de estos atajos hace algo que no podrías escribir vos. Todos existen porque el código
largo era **fácil de olvidar** (`close()`), **fácil de romper** (`asistencia[dni]`) o
**incómodo de leer**.

Cuando veas uno nuevo en el proyecto, la pregunta no es "¿qué es esta magia?". Es
**"¿cómo lo escribiría sin esto?"**. Si tenés la respuesta, ya lo entendiste.
:::
