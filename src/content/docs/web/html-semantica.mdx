## El problema

Una página real tiene partes que se repiten en todas: una **cabecera** con el nombre, un **menú**,
el **contenido** y un **pie** con los datos de contacto. Con lo que sabemos, todo eso sería un
montón de párrafos y títulos sueltos, y nadie —ni vos, ni Google, ni un lector de pantalla— sabría
dónde empieza el menú y dónde el contenido.

Y el sistema de asistencias necesita dos cosas que todavía no sabemos hacer: **la planilla del día**,
que es una tabla, y **el formulario de inscripción**, donde la persona escribe sus datos.

## Las partes de una página, con nombre

HTML tiene etiquetas que no cambian cómo se ve nada: **dicen qué es cada parte**.

| Etiqueta | Es… |
|---|---|
| `<header>` | La cabecera: el nombre, el logo |
| `<nav>` | El menú de navegación: los links a las secciones |
| `<main>` | **El contenido principal.** Uno solo por página |
| `<section>` | Una sección con su título, como un capítulo |
| `<article>` | Algo que se entiende solo: una noticia, un producto, una tarjeta |
| `<footer>` | El pie: contacto, dirección, horarios |

```html
<body>
  <header><h1>CFP 401</h1></header>
  <nav>
    <a href="#cursos">Cursos</a>
    <a href="#contacto">Contacto</a>
  </nav>
  <main>
    <section id="cursos">...</section>
  </main>
  <footer id="contacto">Calle 2 nro 401, Ensenada</footer>
</body>
```

Antes todo se hacía con `<div>`, que es **una caja sin significado**: sirve para agrupar, pero no
dice qué hay adentro. Sigue existiendo, y se usa cuando ninguna de las de arriba corresponde.

:::note[¿Para qué, si se ve igual?]
Un lector de pantalla tiene un atajo para **saltar al contenido** y no escuchar el menú en cada
página: lo encuentra por el `<main>`. Y Google le da más importancia a lo que está en el `<main>`
que a lo que está en el `<footer>`. Las etiquetas con significado son **gratis**: ocupan lo mismo
que un `<div>`.
:::

## Tablas: la planilla del día

Una tabla se arma **por renglones**. Cada renglón es un `<tr>` (*table row*), y adentro van sus
celdas: `<th>` si es un título de columna (*table header*), `<td>` si es un dato (*table data*).

```html
<table>
  <thead>
    <tr><th>DNI</th><th>Nombre</th></tr>
  </thead>
  <tbody>
    <tr><td>30111222</td><td>Ana Gómez</td></tr>
    <tr><td>28999888</td><td>Luis Paz</td></tr>
  </tbody>
</table>
```

| Etiqueta | Es… |
|---|---|
| `<table>` | La tabla entera |
| `<thead>` | El renglón de los títulos |
| `<tbody>` | Los renglones de datos |
| `<tr>` | Un renglón |
| `<th>` / `<td>` | Una celda de título / de dato |

Si te suena, es porque **es una lista de listas**: la tabla es una lista de renglones, y cada
renglón es una lista de celdas. Como `[["30111222", "Ana Gómez"], ["28999888", "Luis Paz"]]`.

:::caution[Las tablas son para datos en tabla]
Hace veinte años se usaban para acomodar cosas en la página: el menú en una celda, el contenido en
otra. **No.** Para eso está CSS. Una tabla es para lo que en papel sería una planilla.
:::

## Formularios: que la persona escriba

Un formulario junta **campos** donde la persona completa datos, y un botón para mandarlos:

```html
<form>
  <label for="nombre">Nombre</label>
  <input id="nombre" type="text">

  <label for="email">Correo</label>
  <input id="email" type="email">

  <button>Inscribirme</button>
</form>
```

- `<input>` es el campo. **No se cierra**, como `<img>`.
- `type` dice **qué se escribe**, y el navegador ayuda según eso: con `email` revisa que tenga @, con
  `number` solo deja números, y en el celular **muestra el teclado que corresponde**.
- `<label>` es el **cartel** del campo. Su `for` tiene que ser igual al `id` del campo.

| `type` | Para… |
|---|---|
| `text` | Texto cualquiera |
| `email` | Un correo |
| `number` | Un número |
| `tel` | Un teléfono (en el celular, el teclado de números) |
| `date` | Una fecha, con un calendario |
| `checkbox` | Una casilla de sí o no |

Para elegir **una opción de una lista**, `<select>`, con un `<option>` por opción:

```html
<label for="turno">Turno</label>
<select id="turno">
  <option>Mañana</option>
  <option>Tarde</option>
</select>
```

:::note[¿Y adónde se manda?]
Con HTML solo, el botón **no tiene adónde mandar los datos**: hace falta un programa del otro lado
que los reciba y los guarde. Ese programa, en Python, es justamente lo que vas a hacer con **Flask**
en el sistema de asistencias. Por ahora, el formulario se arma y se ve.
:::

## Para llevar

- Etiquetas **con significado**: `<header>`, `<nav>`, `<main>` (uno solo), `<section>`,
  `<article>`, `<footer>`. `<div>` es una caja sin significado, para cuando ninguna corresponde.
- **Tablas**: `<table>`, con `<thead>` para los títulos y `<tbody>` para los datos. Cada renglón un
  `<tr>`, cada celda un `<th>` (título) o `<td>` (dato). Son para datos, no para acomodar la página.
- **Formularios**: `<form>`, con un `<input>` por campo y el `type` que corresponde (`text`, `email`,
  `number`, `tel`, `date`…). `<select>` con `<option>` para elegir.
- **Cada campo con su `<label>`**: el `for` del label igual al `id` del campo.
- Mandar los datos necesita un programa del otro lado: eso es Flask.
