## El problema

Es la Expo, son las seis de la tarde, y alguien de Pastelería completa el formulario desde el
celular. Una preceptora lo revisa y tilda *Aprobado*. ¿Y ahora?

Hasta acá, el catálogo aparece cuando **alguien** baja la planilla, corre `generar.py` en su compu y
sube el resultado. Si nadie lo hace, no aparece. Y si lo hace con un error en el programa, se publica
roto.

Lo que queremos: que **cada hora**, sin que nadie apriete nada, una computadora **pruebe** el
programa, lo **corra** y **publique** el resultado. Y que si algo anda mal, **no publique nada**.

## CI y CD

Son dos ideas, y casi siempre van juntas:

- **CI, integración continua** (*continuous integration*): cada vez que cambia el código, una
  computadora **corre los tests** sola. Si alguno falla, avisa enseguida: el error aparece cuando se
  cometió, y no tres semanas después.
- **CD, entrega continua** (*continuous delivery/deployment*): si los tests pasan, esa misma
  computadora **publica** el resultado. Sin pasos a mano, que es donde se cuelan los errores (subir
  la carpeta equivocada, olvidarse un archivo).

Juntas forman una **cañería** (*pipeline*): bajar el código → instalar lo que hace falta → los tests
→ generar → publicar. Cada paso se hace solo si el anterior salió bien.

## GitHub Actions

GitHub tiene computadoras que presta gratis para esto. Se les dice qué hacer con un archivo en el
repo, en `.github/workflows/`, escrito en **YAML**: un formato para escribir datos con sangría, como
un diccionario de Python sin llaves.

Este es el de los catálogos, por partes.

### Cuándo corre: `on`

```yaml
on:
    schedule:
        - cron: "17 * * * *"    # cada hora, en el minuto 17
    workflow_dispatch:           # el botón "Run workflow", para no esperar a la hora
    push:
        branches: [main]         # y cada vez que se cambia el código
```

Son los **disparadores**. Tres cosas lo hacen correr: el reloj, un botón, y un cambio en el código.

El `cron` es una forma muy vieja (de los años 70) de decir "cada cuánto". Son cinco campos:
**minuto, hora, día, mes y día de la semana**, y `*` quiere decir "cualquiera":

| `cron` | Cuándo |
|---|---|
| `17 * * * *` | En el minuto 17 de cada hora |
| `0 9 * * *` | Todos los días a las 9:00 (hora UTC: 6:00 en Argentina) |
| `0 9 * * 1` | Los lunes a las 9:00 UTC |

### Dónde y qué: `jobs` y `steps`

```yaml
jobs:
    publicar:
        runs-on: ubuntu-latest          # una compu con Linux, prestada, que se borra al terminar
        steps:
            - name: Bajar el código
              uses: actions/checkout@v4

            - name: Instalar Python
              uses: actions/setup-python@v5
              with:
                  python-version: "3.12"

            - name: Instalar lo que hace falta
              run: pip install -r requirements.txt

            - name: Los tests (si alguno falla, no se publica nada)
              run: pytest -q

            - name: Generar los catálogos
              run: python generar.py

            - name: Publicarlo
              uses: actions/deploy-pages@v4
```

Cada **paso** (*step*) es una de dos cosas:

- **`run`**: un comando, el mismo que escribirías en la terminal.
- **`uses`**: una **acción** que ya hizo alguien (bajar el código, instalar Python, publicar en
  GitHub Pages). Es como un `import`: usás algo hecho en vez de escribirlo.

La compu que presta GitHub se llama **runner**. Arranca vacía, hace los pasos en orden, y al terminar
se borra. Por eso el primer paso es bajar el código: no tiene nada.

## Los secretos

Para leer la planilla, el programa necesita **permiso de Google**: una llave, un archivo JSON. Pero
el repo es **público**: cualquiera puede leer todo lo que está ahí. Si la llave va en el código,
cualquiera puede leer la planilla, con los correos y teléfonos de todos.

Por eso GitHub tiene **secretos**: valores que se guardan en el repo (*Settings → Secrets*), que
nadie puede ver, ni siquiera quien los cargó, y que el workflow recibe como variables:

```yaml
            - name: Generar los catálogos
              env:
                  GOOGLE_CREDENTIALS: ${{ secrets.GOOGLE_CREDENTIALS }}
              run: python generar.py
```

Y el programa lo lee de ahí, como cualquier variable del sistema:

```python
import os

credenciales = os.environ.get("GOOGLE_CREDENTIALS")
```

:::caution[Si una llave se publica por error]
Borrarla del repo **no alcanza**: queda en la historia de Git, y hay programas que recorren GitHub
buscando llaves todo el día. Lo que hay que hacer es **anularla** (en Google, borrar esa clave y crear
otra) y cargar la nueva como secreto.
:::

## Los tests que cuidan la publicación

En la cañería, los tests son **la red de seguridad**: lo único que está entre un error y un catálogo
roto en internet. Y un test que no prueba los casos difíciles es una red con agujeros.

`"$4.500"`, y si lo dejó vacío, `"Consultar"`. Parece fácil, pero la gente escribe cualquier cosa.

## El último control: los datos

Los tests prueban **el programa**. Pero antes de publicar también hay que mirar **los datos**: una
respuesta puede estar aprobada y tener igual algo que no anda (alguien editó la planilla a mano y
dejó un WhatsApp de 6 números). El programa no tiene que publicarla rota: la **saltea** y deja dicho
por qué, en el registro del workflow, para que alguien la arregle.

## Para llevar

- **CI**: una computadora corre los tests cada vez que cambia el código. **CD**: si pasan, publica.
  Juntas, una **cañería** que se corta en el primer paso que falla.
- En GitHub, la cañería es un **workflow** en `.github/workflows/`, en YAML: **cuándo** corre (`on`:
  el reloj con `cron`, un botón, un cambio) y **qué hace** (`steps`, con `run` o `uses`).
- Los **tests van antes de publicar**: si uno falla, en internet queda lo de antes.
- Las llaves y contraseñas van en **secretos**, nunca en el código. Si una se publica, se **anula**.
- Antes de publicar se revisa el programa (los tests) y también **los datos**: lo roto se saltea, y
  queda dicho por qué.
